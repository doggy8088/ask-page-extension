# 工具治理層觀察方式

這份文件記錄**如何觀察工具治理層（Governed Tool Execution）的運作狀態**，供日後維護與除錯參考。

架構與決策背景請見 [GOVERNED_TOOL_EXECUTION.md](GOVERNED_TOOL_EXECUTION.md)；本文件只談「怎麼看」。

---

## 一句話現況

> **治理層確實在跑，但稽核紀錄目前沒有接收者，DevTools console 看不到任何東西。**

這不是 bug，是目前的設計狀態：治理層為「觀察」而存在，但觀察者（稽核 UI）留待後續 PR 實作。

另外要注意：治理層跑在 content script 的 **isolated world**（`manifest.json` 未指定 `world`，預設即 ISOLATED），與頁面 console 的 `globalThis` 不是同一個物件。這影響到「從頁面 console 掛鉤」這種觀察方式能否運作。

---

## 先確認治理層到底有沒有在跑

### 現況事實

現行 `toolContext` 只帶三個欄位（`content.js` 的 `runOpenAIStyleToolLoop` 呼叫處）：

```js
toolContext: {
    webSearch: { fetchImpl, signal, task }
}
```

**沒有** `governanceMode`，**沒有** `onToolAudit`。

而治理層的稽核輸出只走 `onAudit` 回呼（`lib/tool-governance.js`）：

```js
const emitAudit = (record) => {
    if (!record || typeof onAudit !== 'function') {
        return;   // ← 現行情況：直接靜默返回，紀錄被丟棄
    }
    ...
};
```

治理層本身也**完全沒有 `console.log`**，所以稽核紀錄不會出現在 DevTools console。

### 實測結果

| 情境 | 治理層有跑嗎 | 產生的稽核紀錄 |
|---|---|---|
| 現行 production toolContext | ✅ 有跑 | 0 筆（無接收者，靜默丟棄） |
| 額外傳入 `onToolAudit` | ✅ 有跑 | 1 筆，欄位完整 |

## 觀察方式一：DevTools Network 看模型收到的工具描述

風險標註會直接進入送給模型的 request payload。

**步驟**

1. 開啟頁面 DevTools → **Network** 分頁
2. 篩選 Gemini / OpenAI 的請求（依你使用的 provider）
3. 點開請求 → **Request Payload**
4. 找 `tools` 陣列，看每個工具的 `description` 開頭

**會看到**

```json
{
  "type": "function",
  "name": "read_page",
  "description": "[tool-risk: read-only] 讀取頁面內容",
  "parameters": { ... }
}
```

**各 provider 的位置**

| Provider | Payload 路徑 |
|---|---|
| OpenAI Chat Completions | `tools[].function.description` |
| OpenAI Responses | `tools[].description` |
| Gemini（Interactions API） | `tools[].description` |

> **注意**：Gemini 沿用上游 Interactions API 的 `{type:"function"}` 格式，**不是** `functionDeclarations`。這個格式是硬性約束，見 `tests/governance-runtime-guard.test.js`。

```bash
node tests/governed-execution.integration.test.js
```

### 稽核紀錄的實際欄位

```js
{
  version: 1,
  timestamp: '2026-10-20T06:31:50.939Z',
  toolCallId: '2',              // 工具呼叫 ID
  toolName: 'read_page',        // 工具名稱
  risk: 'read-only',            // 風險層級
  governanceMode: 'observe',    // 治理模式
  decision: 'allow',            // allow / require-approval / block
  approval: 'not-requested',    // not-requested / approved / denied / error / unavailable / not-available
  outcome: 'executed',          // executed / blocked / error
  success: false,               // 工具本身是否成功
  durationMs: 0,                // 執行耗時
  error: null                   // 截斷到 500 字元的錯誤訊息
}
```

### 欄位值完整清單

**`decision`**

| 值 | 意義 |
|---|---|
| `allow` | 直接放行 |
| `require-approval` | 需要明確核准（observe 模式仍放行，僅標記） |
| `block` | 擋下 |

**`approval`**

| 值 | 意義 |
|---|---|
| `not-requested` | 未觸發核准流程 |
| `approved` | 已核准 |
| `denied` | 核准被拒 |
| `error` | 核准流程拋錯 |
| `unavailable` | 需要核准但沒有核准機制 |
| `not-available` | 治理層缺席，或參數無法快照 |

**`outcome`**

| 值 | 意義 |
|---|---|
| `executed` | 已執行 |
| `blocked` | 被擋下，未執行 |
| `error` | 執行時拋錯 |

## 觀察方式三：在 console 掛稽核接收者

`AskPageToolGovernance` 是 `Object.freeze` 凍結的，**不能**直接改它的屬性：

```js
AskPageToolGovernance.executeGovernedToolCall = fn;  // ✗ 靜默失敗（非 strict mode）
```

可行做法是整個換掉 `globalThis` 上的參考：

```js
// 在頁面 console 執行
const __orig = AskPageToolGovernance;
globalThis.AskPageToolGovernance = Object.freeze({
  ...__orig,
  executeGovernedToolCall: (opts) => {
    const origAudit = opts.onAudit;
    opts.onAudit = (record) => {
      console.log('[governance]', record);
      origAudit?.(record);
    };
    return __orig.executeGovernedToolCall(opts);
  }
});
```

> **限制（重要）**：content script 執行在 **isolated world**，與頁面 console 的 `globalThis` **不是同一個物件**。所以在頁面 console 讀到的 `AskPageToolGovernance` 通常是 `undefined`，這個方法多數情況下**看不到** content script 內部的治理呼叫。要觀察 content script 內部，請用方式四。

---

## 觀察方式四：在 `content.js` 加 console 觀察點

最直接、也最可靠的方法。改 `content.js` 的 `executeToolCall`：

```js
onAudit: toolContext.onToolAudit || ((record) => {
    console.log('[AskPage][governance]', record);
}),
```

改完在頁面 DevTools console 就能看到每個工具的完整治理紀錄。

**實測輸出**（production toolContext，無 `onToolAudit`）：

```
[AskPage] Executing tool: read_page {"mode":"text"}
[AskPage][governance] {"version":1,"timestamp":"2026-10-20T06:43:08.909Z","toolCallId":"1","toolName":"read_page","risk":"read-only","governanceMode":"observe","decision":"allow","approval":"not-requested","outcome":"executed","success":false,"durationMs":0,"error":null}
```

> 治理紀錄的物件是無原型物件（`Object.create(null)`），在 console 展開檢視正常，但若要 `String(record)` 會拋 `TypeError: Cannot convert object to primitive value`。要取字串請用 `JSON.stringify(record)`。

**取捨**

- 優點：即時、完整、可以看到 `content.js` 真實執行路徑
- 缺點：這是開發用輔助，會污染正式版 console。正式提交前應拿掉，或改成只在 `enforce` 模式或特定旗標下輸出

## 風險分類對照表

由 `lib/tool-policy.js` 決定，**所有 provider 共用同一份**（`getToolDefinitionsForRequest` 統一標註）。

| 工具 | 風險 | 需要明確核准 |
|---|---|---|
| `web_search` | `read-only` | 否 |
| `get_page_metadata` | `read-only` | 否 |
| `inspect_selection` | `read-only` | 否 |
| `inspect_form_fields` | `read-only` | 否 |
| `read_page` | `read-only` | 否 |
| `find` | `read-only` | 否 |
| `get_page_text` | `read-only` | 否 |
| `click` | `external-side-effect` | 是 |
| `type` | `external-side-effect` | 是 |
| `select_option` | `external-side-effect` | 是 |
| `fill_form_fields` | `external-side-effect` | 是 |
| `run_js` | `high-impact` | 是 |
| 其他任何名稱 | `unknown` | 是 |

### 參數影響分類

`type` 與 `fill_form_fields` 帶 `submit: true` 時維持 `external-side-effect`（已是此層級，不再升級）。

### 布林正規化必須與執行層一致

政策層的 `coerceSubmitFlag` 與 `content.js` 的 `coerceBooleanValue` 必須語意相同。以下視為 `true`：

```
'true'、'1'、'yes'、'on'、'checked'、'selected'、'是'、'需要'、'勾選'
```

正規化會去除空白、轉小寫、移除標點符號（`！!?，,。:：;；"'` 等）後再比對。

> 為什麼重要：任一處放寬都會讓 `enforce` 模式出現可繞過的缺口。`type` 帶 `submit:'true'` 若被政策層判為 `false`、執行層卻當成 `true` 送出表單，就等於核准機制被繞過。

### 未知工具的處理

`classifyToolRisk` 使用 `Object.prototype.hasOwnProperty.call`，**只認取自己的屬性**。因此 `constructor`、`toString`、`__proto__`、`valueOf`、`hasOwnProperty` 這些繼承自 `Object.prototype` 的名稱都會落到 `unknown`，不會被誤判成已知工具而跳過核准。

## 兩種模式

| | observe（預設） | enforce |
|---|---|---|
| 風險分類 | ✅ | ✅ |
| 稽核紀錄 | ✅（目前無接收者） | ✅ |
| 需要核准的工具 | 標記但**照常執行** | **擋下**，等核准 |
| 治理模組缺席 | 照常執行既有工具 | **擋下**（fail-closed） |
| 核准被拒 | 不適用 | **擋下** |
| 核准後前置驗證失敗 | 不適用 | **擋下** |
| 現有使用者行為 | **完全不變** | 會改變（尚未啟用） |

> **enforce 目前未被啟用**：需要呼叫端提供 `governanceMode: 'enforce'` 與核准／前置驗證回呼，現行 UI 都沒有提供。

---

## fail-closed 情境一覽

`enforce` 模式下，以下情況一律擋下並留下 `blocked` 稽核紀錄：

| 情境 | `error` 欄位 |
|---|---|
| 治理模組不可用 | `governance-module-unavailable` |
| 缺少核准機制 | `missing-approval-handler` |
| 核准流程拋錯 | 原始錯誤訊息 |
| 核准被拒 | （無，`approval: 'denied'`） |
| 核准後缺少前置驗證 | `missing-precondition-validator` |
| 前置驗證未通過 | `precondition-rejected` |
| 前置驗證拋錯 | 原始錯誤訊息 |
| 缺少執行 handler | `missing-execution-handler` |
| 參數快照失敗（巢狀過深） | `argument-snapshot-failed` |

`observe` 模式下，上述情境**全部照常執行**（唯一例外是參數快照失敗，因為參數無法處理時工具本來就無法執行）。

## 稽核是旁路觀察

稽核寫入失敗**不會**改變工具執行結果。同步拋錯與非同步拒絕都被隔離，只會在 console 留下 warning：

```
[AskPage] Tool audit callback failed: ...
[AskPage] Async tool audit callback failed: ...
```

這是刻意的：稽核是觀察機制，不該有能力讓使用者的操作失敗。

---

## 參數快照的限制

工具參數來自模型輸出，屬於不可信輸入。

- **深度上限 32 層**：超過時擲出 `ToolArgumentSnapshotError`，由治理層轉成失敗的工具結果（`success: false`）與 `blocked` 稽核紀錄，不會以 `RangeError` 中斷整輪代理
- **無原型物件**：快照使用 `Object.create(null)` 搭配 `Object.defineProperty`，避免 JSON 解析出的 `"__proto__"` 鍵走成 prototype setter，讓快照憑空繼承出 `submit` 等旗標
